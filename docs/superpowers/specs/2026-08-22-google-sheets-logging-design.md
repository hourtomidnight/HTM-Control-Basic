# Google Sheets Logging — Design

Status: approved for planning
Date: 2026-08-22

## Purpose

HTM-Control-Basic (the Room Control / Timer app) currently has no
persistence — game state lives only in the browser tab running
`game.js`, and nothing survives a reset or a power loss. This adds
live, incremental logging to Google Sheets so that:

- Every game session is tracked (start time, duration, adjustments,
  hints given, team/operator/player info, notes) for game-quality
  analysis, in the same spirit as the existing session tracker
  (`tracker/` in the GameTracker repo).
- Hint usage is logged per event, per room, to answer "does this
  puzzle always need a hint? if so, redesign it."
- Data is written incrementally as events happen, not batched at the
  end of a session — if the Pi loses power mid-game, whatever
  happened up to the last event is already in the sheet.

## Context / constraints

- Each physical deployment of this app will eventually run on its own
  dedicated Raspberry Pi wired to one specific escape room's GPIO
  hardware. This current instance (`HTM-Control-Basic` on the shared
  Pi at `hourtomidnight`/`100.109.138.91`) is a test/dev instance, not
  a real room. GPIO/Modbus integration is explicitly **out of scope**
  for this feature — the design should not preclude adding it later,
  but nothing here builds it.
- Because each deployment is dedicated to one room, "which room this
  is" is a **config-time** setting (admin screen), not something the
  operator picks per session.
- `server.js` currently has no npm dependencies (Node built-ins only)
  and no `package.json` install step. This feature is the first thing
  to require an npm dependency (`googleapis`), matching the pattern
  already used by `tracker/server.js` in the GameTracker repo.
- All operator actions (start, stop, pause, resume, add/sub time,
  show/dismiss hint, escaped, reset) already flow through a single
  chokepoint: `POST /cmd` on the server, which then broadcasts to all
  connected clients over SSE (see `channel.js`, `server.js`). This is
  the natural place to observe events server-side without touching
  the client-side timer logic in `game.js`.
- The existing Session Tracker (`tracker/`) writes to a spreadsheet
  with ID `1TCrSmXbHZnlltAJn1940vrMo_Z6z3PuLskcGPSQu7Yk`, using a
  service-account credentials file (`google-credentials.json`,
  gitignored) and the `googleapis` npm package. Its "Drop Down
  options" tab, column B, holds the list of operator names — this
  feature reads that list (read-only) for the operator dropdown here.

## Data destinations

Two independent, separately configured Google Sheets destinations.
Both spreadsheet ID + tab name are set once in the admin/config screen
(`config.html`), since each deployment is permanently bound to one
room.

### 1. Game Sessions (1 row per game)

One row per game, created at `start` and updated in place as the game
progresses, finalized at `escaped`/`reset`.

Columns:
- Date
- Start Time
- Room (from config, not per-session input)
- Operator (dropdown, sourced from tracker's "Drop Down options"
  column B)
- Team Name (free text)
- New Players (count)
- Experienced Players (count)
- End Time
- Duration
- Status (Escaped / Reset-Lost)
- # Time Adjustments
- Net Time Adjusted (e.g. `+3:00`, `-1:30`)
- Hint Count
- Notes (free text, operator-editable during the game)

### 2. Hint Library (event log + reference)

Separate spreadsheet (may be the same physical spreadsheet as #1 or a
different one — configured independently). Two kinds of tabs:

- **Hotkeys reference tab** (one shared tab) — a synced dump of this
  room's configured hint groups/keys from `config.json`, for reference
  ("what does F4 show"). Rewritten whenever hint config is saved, not
  incrementally.
- **Per-room event log tab** (one tab per room; this deployment writes
  to the tab configured for its own room) — one row appended
  immediately each time a hint is shown:
  - Date
  - Time
  - Hint Text
  - Session Start Time (join key back to the Game Sessions row)

No chart/summary is generated by the app. The per-room event log tab
is plain, appendable data; a pivot table/chart is built once in Sheets
on top of it by hand and updates automatically as rows are appended.
This avoids taking on the Sheets Charts API.

## Write timing (incremental, for outage resilience)

- `start` → append new Game Sessions row immediately with whatever is
  known at that moment (date, start time, room, operator, team name,
  player counts if already filled in). Remember the row index for the
  rest of the session.
- `add-min` / `sub-min` / `add-sec` / `sub-sec` → update the session
  row's adjustment count + net adjustment immediately.
- `show-hint` → (a) append a row to the room's Hint Library event log
  tab immediately, and (b) update the session row's hint count.
- Notes field edits → debounced (write ~5s after the operator stops
  typing, or on blur) rather than on every keystroke, to avoid
  hammering the Sheets API while still being "live."
- Team Name / player counts, if edited after `start` (they're
  operator-editable throughout, not gated behind starting the game) →
  update the session row on change (debounced like notes).
- `escaped` / `reset` (while a session is active) → final update to
  the session row: end time, duration, status. Session then clears
  server-side, ready for the next game.
- If Sheets isn't configured (missing credentials file or empty
  spreadsheet ID in config) → all of the above no-ops silently, same
  fallback behavior as the tracker app.

## New UI

**Operator screen** (`operator.html`/`operator.js`) — new fields,
visible and editable at any time (not a separate pre-game form/gate):
- Team Name (text)
- Operator (dropdown, populated from tracker's spreadsheet)
- New Players (number)
- Experienced Players (number)
- Notes (textarea)

**Config screen** (`config.html`) — new "Game Sheets" card:
- Room Name (this deployment's identity)
- Game Sessions: Spreadsheet ID, Tab name
- Hint Library: Spreadsheet ID, Tab name (event log), Hotkeys
  reference tab name
- Enable/disable toggle (or simply: blank spreadsheet ID = disabled)

## Server-side implementation shape

- New module, e.g. `sheets.js`, mirroring `tracker/server.js`'s
  Google Sheets setup (service account auth via
  `google-credentials.json`, `googleapis` package).
- `server.js` gains an in-memory `currentSession` object populated and
  mutated as commands pass through the existing `/cmd` handler. No
  change to `game.js`'s authoritative timer logic — the server is
  purely observing the same commands it already relays.
- `package.json` gains `googleapis` as a real dependency; this is the
  first feature requiring `npm install` on deploy (setup docs/scripts
  will need a one-line update).
- Sheets write failures are caught and logged, never block the
  in-browser game (matches tracker's existing error handling
  approach).

## Explicitly out of scope (for this feature)

- GPIO / Modbus integration (future, dedicated-Pi-per-room work).
- Per-session room switching (room is fixed per deployment via
  config).
- App-generated charts (left to native Sheets features).
- Multi-operator concurrent editing conflict handling beyond what
  "last write wins" on debounced field updates naturally gives.

## Open questions for implementation planning

- Exact debounce interval for Notes/Team Name/player-count updates.
- Whether the Hotkeys reference tab layout should mirror the
  `config.json` hint-groups structure directly or something flatter.
- Credentials: confirmed reuse of the tracker's existing
  `google-credentials.json` (same service account), copied into this
  app's directory (gitignored, not committed) — same access-grant
  model as the tracker, no new Google Cloud setup needed unless the
  destination spreadsheets aren't already shared with that service
  account's email.
